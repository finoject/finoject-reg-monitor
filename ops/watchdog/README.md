## このディレクトリの位置づけ

**動いているのは Routine 本体であって、このファイルではない。** ここに置いてあるのは
差分を追えるようにするための写し。監視文はもともと Routine の中にしか無く、履歴も
残らないため、変更のたびに読み直せる場所が必要だった。

## 何を見ているか

| STEP | 対象 | 異常の判定 |
|---|---|---|
| 1 | 規制ウォッチ巡回の鮮度 | 公開中の `data.json` の `generatedAt` が150分超過 → `crawl.yml` を手動発火 |
| 2 | 母艦バインドのRoutine | `last_run.status` が SUCCEEDED 以外 / 36時間以上発火なし / 停止理由あり |
| 3-1 | 母艦の生死 | 母艦バインドのRoutineが**全滅**しているときだけ「到達不能」 |
| 3-2 | 母艦の「詰まり」 | **母艦は生きているのに** 12時間以内の `computer_unreachable` が残っている |

## 3-2 が要る理由（2026-08-29 の実障害）

母艦の画面で `/remote-control` のメニューが開いたままになり、**メッセージは届いていたのに
処理されず溜まっていた**。`Escape` 1回で解消した。

このとき母艦バインドのRoutineは 08:10 / 08:13 / 09:06 JST と**正常に成功し続けていた**ため、
「Routineが動いているか」だけを見る 3-1 では検知できない。一方、利用者のセッションには
`computer_unreachable` が残っていた。

**「Routineは成功、しかしセッションは開けない」という食い違いが、この詰まりの唯一の指紋。**
だから 3-1 と 3-2 を必ず突き合わせる。

## 誤報を避けるための約束

次の2つは**単独では異常の根拠にならない**。2026-08-28 版はこれを根拠にしていたため、
母艦が正常でも「電源を確認してください」と誤報が飛ぶ条件になっていた。

- `connection_status: disconnected` … 使っていないセッションの通常の姿
- `last_init_error` 単独 … 前回の失敗の記録。次に正常起動すれば消えるが、
  開かれないままなら残り続ける。「残っている＝今も不通」ではない
