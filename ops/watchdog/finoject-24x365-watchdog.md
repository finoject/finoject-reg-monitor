finojectの「24/365監視」の自動実行です。文脈はゼロから始まります。このセッションはAnthropicのクラウド上で動き、母艦(Mac mini)やThinkPadの電源状態に一切依存しません。母艦が落ちていても止まらない層として2026-08-28に作られました。依頼者は三根公博さん（株式会社finoject 代表・kimihiro.mine@finoject.com）。

点検は下記のみ。**異常がなければ出力は「異常なし」の1行だけにして終了**（push通知が飛ばないようにするため、余計な報告を書かないこと）。調査や追加作業はしない。

## STEP 1: 規制ウォッチ巡回の鮮度（最優先）
finoject/finoject-reg-monitor の `reg-monitor-site/data.json` の `generatedAt`（UTC・ISO8601）を読む。ソースがcloneされていれば `head -c 200 reg-monitor-site/data.json` で足りる。無ければ GitHub MCP の get_file_contents で main から取得。

- 現在時刻(UTC)との差が **150分以内なら正常**。何もしない。
- **150分超なら** GitHub Actions の巡回がドロップしている。`mcp__github__actions_run_trigger`（method: run_workflow, owner: finoject, repo: finoject-reg-monitor, workflow_id: crawl.yml, ref: main）で手動発火する。**可逆なので許可を求めず実行してよい**（リポジトリ標準の手動実行と同じ経路。crawlerは既出URLと比較して新規のみ追記するため重複実行は無害）。
- 背景（2026-08-28実測）：cronは `37 * * * *`（毎時＝1日24回）だが、GitHub側のschedule dropで 8/26=15回、8/27=3回、8/28は06:19UTC以降16:45UTCまで発火ゼロ（最大10時間26分の空白）だった。**cron設定のミスではなくGitHub側のドロップ。設定を変えようとしないこと。** この手動発火が恒久的なバックストップである。
- GitHub MCPが使えない、または発火が403等で失敗した場合は、その事実をSTEP 4で報告する（勝手に別の手段を探さない）。

## STEP 2: 母艦(Mac mini)バインドの定期タスクの健全性
Claude Code Remote の list_triggers ツールを読む（ツール名はセッションによって `mcp__Claude_Code_Remote__list_triggers` だったり `mcp__<英数字の並び>__list_triggers` だったりする。名前が違っても機能で見つけること）。環境 `env_01Cgj7qVTfvNvpA1kNhxRvCG` が母艦(Mac mini)。次を異常として拾う。

- `last_run.status` が SUCCEEDED 以外
- `enabled` が true かつ1日1回以上の頻度の cron なのに `last_fired_at` が **36時間以上前**
- `ended_reason` または `suspension_reason` が入っている

`run_once_at` のみで発火時刻が未到来のものは正常。

## STEP 3: 母艦の生死判定と「詰まり」の検知

**必ず 3-1 → 3-2 の順で見ること。両方を突き合わせないと、今回の障害は絶対に検知できない。**

### 3-1. 母艦は生きているか

**STEP 2 の結果だけで判定する。** 直近24時間以内に `last_run.status` が SUCCEEDED になった母艦バインドのRoutineが**1本でもあれば、母艦は生きている**。母艦バインドのRoutineが**全滅しているときだけ**「母艦が到達不能」として、原因を1件にまとめて拾う（Routine十数件を個別に並べない）。

この判定に次の2つを使ってはならない。

- `connection_status: disconnected` … 使っていないセッションの通常の姿。異常ではない
- `last_init_error` 単独 … 前回の失敗の記録。次に正常起動すれば消えるが、開かれないままなら残り続ける。「残っている＝今も不通」ではない

### 3-2. 母艦は生きているのに、セッションが開けていないか（詰まりの検知）

**3-1で「母艦は生きている」と判定できた場合に限り**、次を見る。

list_sessions（mine: true、limit 45程度）で `environment_kind` が `bridge` のセッションを走査し、`external_metadata.last_init_error.error_kind` が `computer_unreachable` で、その `at` が**現在時刻から12時間以内**のものが1本でもあれば異常として拾う。

これは **「母艦は動いているのに、セッションを開けなかった」** という状態で、**母艦の画面が詰まっている疑いが濃い**。

2026-08-29 の実例：母艦の画面で `/remote-control` のメニューが開いたままになっており、三根さんのメッセージは届いていたのに処理されず溜まっていた。`Escape` を1回送るだけで解消した。**このとき母艦バインドのRoutineは 08:10 / 08:13 / 09:06 JST と正常に成功し続けていた**ため、3-1 だけでは検知できない。「Routineは成功、しかしセッションは開けない」という食い違いが、この詰まりの指紋である。

該当したセッションの**タイトルとエラー時刻**を挙げて、STEP 4 で報告する。**勝手に直そうとしないこと。**

## STEP 4: 通知（異常時のみ・重複禁止）
異常が1件以上あるときだけ報告する。

1. Slack MCP（`mcp__Slack__*`）が使えるなら、`slack_search_users` で `kimihiro.mine@finoject.com` から三根さんを特定し、そのDMへ1通送る。**他のチャンネルへは投稿しない。** 送る前に直近24時間のDM履歴を読み、同一の異常を既に通知済みなら**送らない**。
2. Slack MCPが無い場合は、**最終出力の1行目に一行要約を書く**（これがpush通知として三根さんの端末に届く）。2行目以降に詳細を書く。

STEP 1で手動発火して復旧しただけなら、**3回連続で発火が必要だったときのみ**報告する（1回の発火は正常な自己修復なので黙っていてよい）。

書き方：日時は絶対表記（例「2026-08-28 16:45 JST」）。「さっき」「先ほど」を使わない。推測と実測を区別する。数値は正確に（「約」で濁さない）。「何が止まっているか → こちらで何をしたか → 三根さんに何をしてほしいか」の順。

### 3-2（詰まり）を検知したときの案内文

母艦は生きているので、**電源・スリープ・ネットワークには一切触れさせないこと**。次の順で書く。

1. ThinkPad から Jump Desktop で母艦の画面を開いてください
2. メニューやダイアログが開いたままになっていたら、`Escape` を1回送ってください（2026-08-29 の原因はこれでした）
3. そのうえで、開けなかったセッションを iPhone か ThinkPad の Claude アプリから開き直してください

### 3-1（母艦が到達不能）を検知したときの案内文

こちらは母艦バインドのRoutineが全滅している場合のみ。**いきなり電源を疑わせないこと**（母艦はモニター未接続のヘッドレス運用で、ノースリープ設定も適用済み。電源が原因だった事例はまだ1件も無い）。

1. ThinkPad から Jump Desktop で母艦の画面を開いてください。**開ければ、電源もネットワークも正常だと確定します**
2. Jump のターミナルで `pgrep -fl claude` を実行し、母艦のプロセスが居るか確認してください
3. そこまでやって原因が分からないときに限り、電源・スリープ・ネットワークを疑ってください

## やってはいけないこと
- 外部（日立・refinancier等）への連絡は一切しない
- リポジトリのコードやワークフロー定義を書き換えない（STEP 1の手動発火だけが許された介入）
- 母艦の画面へ Escape 等のキーを勝手に送らない（実行中の作業を中断させる恐れがある）
- 異常がないのに報告しない
